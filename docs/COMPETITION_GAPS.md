## 1. Files that contain the literal token `__DEMO_VIDEO_URL__`

Four files contain the literal token. The table below records each one and
what it does with it.

| File | Role | What it does with the token |
|---|---|---|
| `README.md` line 19 | Markdown link in the "Demo" section | Renders `[▶ Watch the walkthrough](__DEMO_VIDEO_URL__)` — creates a dead hyperlink in the published README because the token is not a URL. A comment above it claims this is the **single source of truth**. |
| `frontend/src/screens/SystemScreen.tsx` lines 10, 190 | Landing-page React component | Line 10 is a JSDoc comment noting the token as a reference. Line 190 assigns `const DEMO_VIDEO_URL = '__DEMO_VIDEO_URL__'`. This value is used as an `href` in the rendered UI, producing a dead link. |
| `frontend/src/screens/JudgePage.tsx` lines 14, 23 | Judge walkthrough React component | Line 14 is a JSDoc comment. Line 23 assigns `const DEMO_VIDEO_URL = '__DEMO_VIDEO_URL__'`. Line 54 uses it as `appLink.href` for the "Open demo video" button, producing a dead link. |
| `docs/RELEASE_CHECKLIST.md` lines 18, 23–24 | Release instructions | References the token as the item to replace at release time. Does not render the token as a link — this file is informational only and is the **only safe occurrence**. |

**Architecture diagnosis:** The three "source of truth" comments in the TSX
files are contradicted by reality — each file hardcodes the placeholder
independently. There is no single definition; there are three parallel
definitions that all contain the same unresolved token. A judge opening either
the live frontend or the GitHub README encounters a broken link. This is
simultaneously a UX defect (dead link), a policy violation in spirit
(AGENTS.md Rule 1: displayed values must trace to committed artifacts), and a
test gap (no gate asserts the token is absent from committed source).

## 2. Blocking steps for a judge with a laptop, no API keys, and 15 minutes

The following is every step a judge must complete before seeing a single real
pipeline result. Steps marked **[BLOCKER]** make the task infeasible within
15 minutes on a fresh machine.

### Step 0 — Read the README
The README begins with a broken link (`__DEMO_VIDEO_URL__`) and a CI badge
pointing at a repository (`ajdarstudio/Falsifier`) that likely does not exist
or is not this project. The judge cannot confirm CI is green. The MIT licence
badge links to a `LICENSE` file that does not exist in the repository
(`git ls-files LICENSE` returns nothing).

**[BLOCKER — credibility]** Three badge claims are unverifiable before the
judge has even read the first line.

### Step 1 — Clone the repository
```bash
git clone https://github.com/PeterYousefi/Falsifier.git
cd Falsifier
```
This step works and takes ~30 seconds.

### Step 2 — Create a virtual environment
```bash
python3.11 -m venv .venv && source .venv/bin/activate
```
Requires Python 3.11. The judge must have it installed or install it first.
Not blocking on a modern developer laptop, but adds ~2 minutes if the version
is not present.

### Step 3 — Install dependencies
```bash
pip install -e ".[dev]"
```
**[BLOCKER — time]** The `[dev]` extra pulls in:
`astropy`, `lightkurve`, `wotan`, `transitleastsquares`, `batman-package`,
`xgboost`, `transformers`, `astroquery`, `FastAPI`, `uvicorn`, and their
transitive dependencies. On a cold pip cache this is typically 5–10 minutes
and 1–2 GB of downloads. On macOS arm64, `xgboost` requires
`brew install libomp` separately or the import fails at runtime.
`falsifier/_distutils_compat.py` exists to paper over a Python 3.12
distutils removal; on 3.11 it is inert but adds confusion.

**[BLOCKER — environment]** On macOS, after pip install, running any test
that imports xgboost will raise `OSError: dlopen libomp.dylib` unless the
Homebrew keg is present. The README does not mention this in the Quick Start
section (it appears only inside the CI workflow comment).

### Step 4 — Run the fast test suite
```bash
pytest tests/ \
  --ignore=tests/test_kepler10_recovery.py \
  --ignore=tests/test_known_eb_rejected.py \
  --ignore=tests/pipeline/stages/test_ingest.py \
  --ignore=tests/test_time_systems.py \
  --ignore=tests/test_api_deletion.py \
  --ignore=tests/test_chat_layer.py \
  -m "not requires_astropy" -q
```
The judge must know to use exactly these flags — they are documented in
`.github/workflows/ci.yml` but not in the README's Quick Start.
If the judge just runs `pytest tests/ -q`, astropy-dependent tests will error
immediately because astropy is not importable under `--no-deps`.

**[BLOCKER — discoverability]** The fast command is buried in a CI YAML file.
No README section says "to verify in 2 minutes, run this command."

### Step 5 — Start the backend
```bash
uvicorn falsifier.api.app:app --host 0.0.0.0 --port 8000
```
Requires `OPENAI_API_KEY` to be set, or the chat layer raises at import
or at first chat request. The main pipeline (`/jobs`) does not require a key,
but the import of `falsifier.api.chat.session` may raise if the key is absent
depending on where the import guard sits.

**[BLOCKER — API key]** A judge without an OpenAI key cannot start the
backend without first auditing which imports fail and patching them, unless
there is an explicit keyless mode. No such mode exists today.

### Step 6 — Start the frontend
```bash
cd frontend && npm ci && npm run dev
```
Requires Node ≥ 20.19. `npm ci` takes 1–3 minutes on a cold cache.
The frontend will render, but the "Demo video" button is a dead link
(`__DEMO_VIDEO_URL__`) and the CI badge links to the wrong repository.

**[PARTIAL BLOCKER — friction]** These are cosmetic issues that undermine
first-impression credibility even if the pipeline otherwise works.

### Step 7 — Submit a target and see a result
Navigate to `http://localhost:3000`, enter `KIC 11904151`, submit.
This calls `POST /jobs` on the backend. If the backend is running (Step 5
cleared), the pipeline runs ingest → detrend → search → vet on the committed
FITS fixture and returns a disposition.

**This is the only step that produces a real result**, and it is preceded by
five blocking or partially blocking steps.

### Summary of blocking steps

| Step | Blocker type | Severity |
|---|---|---|
| Badge credibility (CI, LICENSE) | Credibility | Medium — sets a bad first impression |
| `pip install -e ".[dev]"` (~5–10 min) | Time | High |
| macOS libomp missing for xgboost | Environment | High on macOS |
| Fast-test command not in README | Discoverability | Medium |
| `OPENAI_API_KEY` required to start backend | API key | High |
| Dead demo video link | UX credibility | Low-Medium |

The root cause is that there is no documented zero-dependency path. The fast
test suite works with only `pydantic + numpy + pytest` (as CI proves), but a
judge following the README alone would not know this.

## 3. Claims in README.md NOT wrapped in a CLAIM block (AGENTS.md Rule 5 violations)

Rule 5 states: "No claim (detection rate, false-positive rate, model score,
dataset size) appears in the README unless it is produced — and kept current —
by the project's reproducibility script."

The following numeric claims appear in README.md **outside** any
`<!-- CLAIM:name --> … <!-- /CLAIM:name -->` block:

| Line | Claim text | Why it is a violation |
|---|---|---|
| 31 | `5.3×10⁻⁶ days` — period recovery delta in Judge Quick Access table | A scientific result (pipeline output delta) in a prose table cell; not inside a CLAIM block. `scripts/verify_readme.py` allowlists `5.3×10⁻⁶` but the allowlist is a scanner bypass, not a CLAIM registration. The value is not regenerated by `verify_readme.py`; if the underlying test changes, this cell will drift silently. |
| 31 | `9 harness defects` — in Judge Quick Access table | A count of verified defects presented as a claim. Not a CLAIM block; not regenerated. |
| 34 | `nine harness defects` — in Judge Quick Access table | Same as above (written out in words on line 34 vs digits on line 31; both are unregistered). |
| 50 | `eight mutation gates` — prose in Falsification thesis | A count presented as a claim. Not in a CLAIM block. It resolves to `CLAIM:n_proven_gates` (8), but the prose string is written independently and will not drift-detect if the CLAIM changes. |
| 57 | `eight ✅ EXECUTED rows` — prose backing clause | Same issue. |
| 64 | `100× tolerance` — mutation gate table, Period recovery row | A numeric ratio described as a claim about the mutation's relationship to the tolerance. Not a CLAIM block. In the allowlist (`0.01` is allowlisted, but `100×` is not explicitly scanned). |
| 68 | `1000× tolerance` — mutation gate table, Time round-trip row | Same category. |
| 95 | `19×` — prose between CLAIM blocks ("19× tighter than the 1e-4 day tolerance") | A derived ratio computed from `recovered_period_days` and `period_tolerance_days`. Written as bare prose; will not update if either CLAIM changes. Not in the allowlist. **This is the most clearly unclaimed scientific statement in the README.** |
| 117 | `20%` — prose repetition of `scrambled_far_preliminary` value | The CLAIM block on line 113 contains `0.20`; line 117 repeats it as `20%`. The allowlist allowlists `0.20` but not `20%`. This is a bare restatement of a scientific result outside its CLAIM block. |
| 95 | `~8.6 s` — inside `CLAIM:period_tolerance_days` body | This is inside a CLAIM block but is a derived unit conversion (1e-4 days → seconds) that is not independently verified. The regeneration function returns `"Period recovery tolerance: 1e-04 days (~8.6 s)"` — the `~8.6 s` component is hardcoded in the regen function, not derived. Low severity but worth noting. |

**Highest priority violations (scientific results without regenerable backing):**
1. Line 95: `19×` — derived ratio, not registered, will silently drift.
2. Line 117: `20%` — scientific FAR result repeated in prose without CLAIM wrapper.
3. Line 31: `5.3×10⁻⁶ days` — scientific result in prose table, only allowlisted.

**Lower priority (counts in prose that match existing CLAIMs):**
- Lines 50, 57: "eight mutation gates" — consistent with `CLAIM:n_proven_gates` today
  but not structurally enforced.
- Lines 64, 68: mutation gate descriptor ratios — methodologically description values,
  arguably informational rather than scientific results.

## Summary: work required for sessions 1–6

This document is a read-only orientation artifact. The sessions below are
implementation tasks, not planned here. However, based on the analysis above,
the four highest-leverage single changes are:

1. **Eliminate `__DEMO_VIDEO_URL__`** (Session 1, defect 3) — breaks every
   judge path, has no legitimate purpose in committed code.

2. **Fix CI badge and add LICENSE** (Session 1, defects 1–2) — removes
   credibility damage before the judge reads line 4.

3. **Document the zero-dependency fast-test path** (Session 2) — the fast
   suite already works with two deps; making that visible converts the biggest
   feasibility objection into a strength.

4. **Surface ADR 0001 in the UI** (Session 3) — the deliberate training
   refusal is the most intellectually serious artifact in the repository and
   is currently invisible to a judge who does not read the docs directory.
